## 2. Método de medición [MEDIDO]
- Binario: `cargo build --release --features diag,tauri/custom-protocol` (`src-tauri/target-diag`, ignorado por Git), con el frontend recién compilado. `diag` solo añade el guion `MIEL_DIAG_SCRIPT` y registros; el instalador no lo incluye.
- `tools/measure.ps1` (árbol de procesos de Miel por PPID, 7 procesos), muestreo cada 5 s tras 20 s de calentamiento; clasificación por estado con `tools/analyze_measure.py` y el registro del motor.
- `MIEL_FAST=1` (acelera los plazos del motor; **no** altera el CSS). Seguimiento desactivado por el guion (`follow_off@1`) para **no depender del cursor**. Guion: `pause@120, resume@180, hide@240, show@300`.
- Equipo: Windows 11 Pro 10.0.26200, 16 procesadores lógicos. No se movió ni se generó ninguna entrada física. Los ajustes reales de la persona se respaldaron antes y se restauraron (comprobado byte a byte).
- Limitaciones: una sola ejecución, 71 muestras (n pequeño por estado), el equipo no estaba aislado de otras cargas; sumar *Working Set* cuenta páginas compartidas varias veces (usar *Private Bytes* para tendencia).

### 3.3 Lectura
1. **El costo en reposo lo domina WebView2 pintando las animaciones CSS** (≈10–13 % de un núcleo con animaciones; ≈0,3–0,6 % sin ellas). `miel.exe` (motor Rust) cuesta ≈0,1 %. **[MEDIDO]** el contraste; que la causa sea precisamente la composición de animaciones infinitas en una ventana transparente es una **[HIPÓTESIS]** razonable pero no aislada por animación individual.
2. **Rest > Idle:** con animaciones, Rest rinde ≈12,7 % frente a ≈11,2 % de Idle (≈ +1,5 puntos; n pequeño, posible ruido). Con movimiento reducido, Rest (0,64) también supera a Idle (0,30). **[HIPÓTESIS]** (no comprobada): en Rest/Sleepy aparece el grupo `zzz` (dos elementos con animación de opacidad y transformación en `bee.css` l.35–36) y las alas siguen animándose con amplitud 0 (`--wing-amp:0deg`, animación infinita activa en `resting`); Idle no tiene `zzz`. **[PENDIENTE]**: aislar con experimentos que desactiven una animación cada vez (requiere tocar CSS de prueba; no autorizado en esta fase).
3. **Paused y Hidden** quedan en ≈0,4–0,5 % (la regla de `app.css` pausa las animaciones). Es el suelo del proceso.
4. **Impacto en el diseño de v0.2.0:** `Sleep` reutiliza `sleepy`/`resting` y, por tanto, hereda el costo de Rest (≈+12 % sobre el suelo, si no se mitiga). Los nuevos sondeos de Rust (decenas de µs por consulta) son despreciables frente a esa cifra; **el riesgo de rendimiento de v0.2.0 es el costo visual del sueño, no el sondeo**. Esto se señala como decisión abierta D10 (§5).

## 5. Presupuestos [PROPUESTA]
No se inventan cifras absolutas. Reglas propuestas, a confirmar:
1. **No empeorar**: ninguna entrega de v0.2.0 puede subir, con significación sobre el ruido observado (≈ ±1 punto en 5 s), Idle, Paused ni Hidden respecto a esta base; Paused/Hidden deben permanecer ≈ suelo (< 1 % de un núcleo) incluso con las funciones nuevas.
2. **Sondeos de Rust**: cada tarea nueva de §4.4 del plan se mide aislando `miel.exe`; objetivo de `miel.exe` ≤ 0,5 % en todos los estados (hoy ≈0,1 %).
3. **Sleep**: no se aprueba como "reposo barato" sin una medición; si resulta ≥ Rest actual, se presentarán alternativas (p. ej., animación reducida mientras duerme) para que la persona apruebe — recordando que **no se cambia arte SVG sin aprobación expresa**; modificar CSS de animación sí es una decisión a aprobar.
4. **Memoria**: sin crecimiento en 6 min de observación; con la ventana de ajustes, medir abierta y tras cerrar; objetivo: volver a ≈ la base (≈ 180 MB Private sumados) tras cerrar.

### Decisión abierta D10
Dado §3.3: ¿se autoriza investigar (en una entrega propia, antes o dentro de E5) una reducción del costo de animación en reposo/sueño? Propuesta: sí, como entrega **E0b** de medición y aislamiento, sin tocar los SVG.
